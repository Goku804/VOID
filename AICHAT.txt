3. IMPORTANT D-CLASS CORRECTION

Previous interpretations of D-Class were incorrect.

The correct meaning is:

D-CLASS = AFTERNOON SCHOOL SLOT

D-Class is NOT a separate academic subject/category.

D-Class means that the user has an afternoon school session.

The actual activity inside D-Class can be:

- LANGUAGE
- LAB

Therefore:

D-Class
↓
Afternoon school session
↓
Language OR Lab

Do NOT create separate "D-Class" academic logic that treats it as another subject.

D-Class scheduling rules

D-Class can occur on ANY school day.

Normal school days:
Monday–Friday.

D-Class can occur on any of those days.

Maximum:
2 D-Class days per week.

The remaining school-day afternoons must remain available for study/planning.

Example only:

Monday → D-Class: Language
Tuesday → Study available
Wednesday → D-Class: Lab
Thursday → Study available
Friday → Study available

This example must NOT be hard-coded.

The user must register/configure their actual D-Class schedule.

D-Class registration

Create appropriate UI under:

SETTINGS
→ SCHEDULE
→ TIMETABLE / CLASSES
→ Register Class

The user should be able to specify:

Day
Activity
Start time
End time
Class type

For afternoon school:

Class type/activity:
LANGUAGE
or
LAB

The system may internally recognize these as D-Class afternoon events if useful, but the UI and database must preserve the actual activity.

Do NOT assume:

- fixed D-Class days
- fixed D-Class times
- fixed Language day
- fixed Lab day
- 2 days every week
- a specific afternoon duration

All must come from user data.

Planner behavior

The planning engine must calculate:

School afternoon occupied by D-Class
+
Available afternoon study time
+
Configured night-study availability

Therefore, if the user has D-Class on only one day, the other afternoons remain available.

If the user has two D-Class days, the other three school-day afternoons can potentially be used for study.

Never hard-code a three-hour afternoon study period.

Add a dedicated AI Chat page to the same VOID application.

This is NOT a fake demonstration chatbot.

The UI may be simple, but the architecture must be real and extensible.

The AI should be able to understand relevant information from the VOID application and provide useful academic planning assistance.

AI Chat purpose

"Which subjects need the most attention?"

"Explain my current plan."

These are examples of behavior, NOT hard-coded commands.

The AI should work with arbitrary natural-language user input.

The AI is an assistant.

The Planning Engine remains responsible for deterministic scheduling and conflict resolution.

For example, if the user asks:

The AI should obtain the real available capacity and relevant tasks, then use the planning logic to determine a sensible recommendation.

12. AI ACTIONS

The AI may eventually recommend actions such as:

- create a temporary plan
- move a task
- adjust a plan
- prioritize an exam
- explain a conflict
- summarize progress

But actions that modify important application data should NOT happen silently.

Use confirmation.

Example:

Move Mathematics from 20:00 to 21:00.

[ APPLY ]
[ CANCEL ]

Only after APPLY should the application modify the database.

The AI should never silently delete or radically modify important academic data.

17. BACKUP SECURITY

Do not assume Telegram storage alone is enough security.

If feasible, encrypt the database backup before uploading it.

The implementation should consider:

- encryption
- backup integrity verification
- backup version
- corruption detection
- restore validation
- safe temporary files
- deletion of temporary decrypted files after use

If a backup is encrypted, design a proper user-controlled recovery secret/password mechanism rather than silently storing an encryption key in the backup itself.

Do NOT send raw sensitive database contents unnecessarily.

18. DO NOT DESTROY CURRENT USER DATA DURING RESTORE

Restore must be deliberate.

Before replacing current database:

- validate backup
- verify version
- verify integrity
- confirm with user
- optionally create a temporary safety backup of the current database if practical

Never overwrite the database immediately just because the user opened the recovery page.
